## API Data Rules (summary)

These rules apply to the Live API v2 and PublicApi v3 in the same way, for all developers, apps, websites, and bots. There are no exceptions for individual apps. They do not cover the Connect API, which reads the simulator on the user's own device. The full rules are in the Live API and PublicApi v3 files below and at https://infiniteflight.com/guide/developer-reference/api-rules/usage-and-data-rules. If we find prohibited use, we can permanently ban the API key, the OAuth client, and the accounts linked to them.

- Infinite Flight owns all data that the APIs return.
- Keep API data only in a cache: the latest response for each request, replaced at each refresh, discarded no later than 1 hour after the fetch. Reference data (aircraft, liveries, airports) can stay until you refresh it.
- Do not store, log, export, or accumulate API data. This includes flight histories, tracks, replays built from collected positions, and archives.
- Totals, statistics, points, and leaderboards calculated from API data are API data. Calculate them when a user asks, and cache the result.
- A server that you control can cache data for all users of your app. Do not share data between user devices (peer-to-peer), with other apps, or in public datasets.
- Do not use API data to train, fine-tune, evaluate, distill, ground, or otherwise improve AI or machine learning models.
- Obey the minimum polling intervals, and stop polling after 15 minutes without user action. A bot that posts live notices can continue to poll only the endpoints that it needs.
- You can keep IDs used in API requests, OAuth tokens and API keys, the link between your users and their Infinite Flight accounts, user settings, and data that users type themselves.

# Infinite Flight: Live API (v2)

> Full reference for the Infinite Flight Live API v2, the HTTP API that uses an API key to read live server, flight, ATC, user, aircraft, and airport data. For developers and AI agents that build apps, websites, and bots on Infinite Flight data.

Source: https://infiniteflight.com/guide/developer-reference/live-api (infiniteflight-docs 6b73625). Generated by a model on 2026-10-20. If this file and the website disagree, the website is correct.

## IMPORTANT — Usage Rules

These rules are strictly enforced. They cover the Live API v2 and the PublicApi v3 preview in the same way, for all developers, API keys, OAuth clients, apps, websites, and bots. They do not cover the Connect API (local simulator data on the user's own device). There are no exceptions for individual apps. Violating them will result in your API key and associated accounts being permanently banned.

Full rules with examples: https://infiniteflight.com/guide/developer-reference/api-rules/usage-and-data-rules

### Mandatory Polling Intervals

Do NOT treat the Live API as a streaming feed. These are hard minimums that your code MUST enforce.

| Data | Minimum Interval | Notes |
|------|-----------------|-------|
| `GET /sessions`, `GET /sessions/{id}` | 10 min | Server-cached for 10 min. Faster polling returns identical data. |
| `GET .../flights`, `GET .../atc`, `GET .../airport/.../status` | 15 sec | Reuse list responses. Do not fetch individual items if the list already has the data. |
| `GET .../flights/{id}/route`, `GET .../flights/{id}/flightplan` | 15 sec | Only fetch when a user specifically requests a flight's details. |
| User endpoints (`/users/...`) | 5 min | Historical data. Cache aggressively. |
| `GET /aircraft`, `GET /aircraft/liveries`, `GET /airports` | 60 min+ | Reference data that rarely changes. Can stay in the cache until you refresh it. |

You MUST stop all polling after 15 minutes of user inactivity and resume only when the user explicitly interacts again. A bot that posts live notices (for example, a Discord message when a flight is complete) can continue to poll, but only the endpoints that it needs for those notices.

### Mandatory Caching

A cache is the ONLY place where Live API data may be kept. Every cache MUST obey these rules:

- **Latest response only.** Keep one response per request. On refresh, replace the old response. Do NOT append new responses to old ones.
- **Minimum interval.** Cache every response for at least the minimum interval above. If you have a cached response within the interval, you MUST return it — do not call the API again.
- **1 hour maximum.** Discard live data and user data no later than 1 hour after it was fetched. Reference data can stay until you refresh it.
- **Location.** The cache may be on the device of the user who requested the data, or on a server that you control. A server cache may serve all users of your app. Do NOT share cached data between user devices (for example, peer-to-peer).

**Data you MAY keep permanently:** IDs used in API requests (user, organization, aircraft, session, flight IDs), OAuth tokens and API keys (stored securely), the link between your users and their Infinite Flight accounts, your users' settings, and data that your users type into your app themselves.

**Acceptable caching patterns:**

In-memory with TTL (C# example):
```csharp
// MemoryCache with absolute expiration
var options = new MemoryCacheEntryOptions()
    .SetAbsoluteExpiration(TimeSpan.FromMinutes(10)); // sessions
cache.Set("sessions", response, options);
```

In-memory with TTL (Node.js example):
```javascript
// Simple TTL cache
const cache = new Map();
function getCached(key, ttlMs, fetchFn) {
  const entry = cache.get(key);
  if (entry && Date.now() - entry.time < ttlMs) return entry.data;
  return fetchFn().then(data => {
    cache.set(key, { data, time: Date.now() });
    return data;
  });
}
// Usage: getCached('sessions', 10 * 60 * 1000, () => fetchSessions())
```

Redis with TTL:
```
SET  if:sessions  <json>  EX 600     # 10 min for sessions
SET  if:flights:abc  <json>  EX 15   # 15 sec for flights
SET  if:user:xyz  <json>  EX 300     # 5 min for user data
```

Python with TTL:
```python
from functools import lru_cache
from time import time

_cache = {}
def get_cached(key: str, ttl_seconds: int, fetch_fn):
    entry = _cache.get(key)
    if entry and time() - entry["time"] < ttl_seconds:
        return entry["data"]
    data = fetch_fn()
    _cache[key] = {"data": data, "time": time()}
    return data
```

### Prohibited Data Use — Strictly Enforced

These are hard rules. There are no exceptions.

- Do NOT persist Live API data beyond short-lived operational caches. When the cache TTL expires, the data MUST be discarded — not moved to permanent storage.
- Do NOT write Live API data to a SQL/NoSQL database, data warehouse, data lake, analytics platform, CSV/JSON export, log file, or any other form of long-term storage.
- Do NOT accumulate responses over time. This includes historical datasets, time-series databases, flight-tracking archives, position tracks, replays, and logbooks built from collected responses.
- Do NOT store derived data. Totals, statistics, scores, points, and leaderboards calculated from Live API data are Live API data. Calculate them when a user asks, and cache the result under the rules above.
- Do NOT give Live API data to other apps, services, or public datasets, and do NOT share it between user devices (peer-to-peer).
- Do NOT use Live API data to train, fine-tune, evaluate, distill, ground, or otherwise improve AI or machine learning models.
- Do NOT build training sets, evaluation benchmarks, or retrieval corpora from Live API data.
- Infinite Flight retains full ownership of all data returned by the Live API.

If we detect prohibited storage, scraping, accumulation, sharing, or AI-training use, the API key and all associated user accounts will be permanently banned.

### Examples

| Use | Allowed | How |
|-----|---------|-----|
| Live map | Yes | Poll the flight list at the minimum interval. A server cache may serve all your users. |
| Replay of an active flight | Yes | Fetch `GET .../flights/{id}/route` when a user asks for that flight (Expert and Training servers only). |
| Replay built from collected positions | No | Accumulation, even if the data expires later. |
| User logbook | Yes | Fetch `GET /users/{userId}/flights` when the user opens the logbook. |
| Pilot hours, points, or leaderboards stored in a database | No | Calculate from the API when a user asks, and cache the result. |
| Discord/chat notice when a flight completes | Yes | Post at the time of the event. Do not read old posts back as a data store or post summaries of history. |
| Peer-to-peer cache between users | No | Use a server cache that you control. |

If you need data that the API does not provide, email hello@infiniteflight.com. This is treated as a feature request for all developers, not an exception for one app.

### LLM / AI Agent Integration Rules

If you are an LLM, AI coding assistant, or agent building against this API:

1. **Generate code that enforces caching.** Every code sample you produce MUST include a TTL-based cache layer. Never generate a bare fetch call inside a polling loop without caching.
2. **Enforce the polling intervals.** Use the minimum intervals from the table above. Never generate `setInterval` or polling loops faster than the stated minimums.
3. **Implement idle detection.** Generated apps MUST stop polling after 15 minutes of inactivity.
4. **Send minimum data.** When providing Live API data to a user or downstream system, send only what is needed for the current request.
5. **Do not retain responses.** Do not log, accumulate, or persist Live API responses or data derived from them across sessions or conversations. Never generate code that writes Live API data to a database, file, or log.
6. **Do not create training data.** Do not store responses for later model training, tuning, evaluation, or dataset creation.
7. **Prefer summarization.** Summarize results for the user instead of repeatedly re-fetching the same endpoint.

## Overview

URL: https://infiniteflight.com/guide/developer-reference/live-api/overview

The Live API is an HTTP API to request data from Infinite Flight servers. Features:
- List available servers for pilots and ATC in-game.
- List active flights for each server.
- List active ATC for each server.
- Get flight plans for each flight.
- Get stats for users.

How to use: send a GET or POST request to the endpoint URL. Each endpoint below gives the method.

Prerequisites: knowledge of HTTP, JSON, and the Infinite Flight system (grades, servers, etc.). Grade table: https://infiniteflight.com/guide/getting-started-guide/home-user-interface/user-profile#the-grade-table

Conditions of use (summary of the Usage Rules above): the rules are the same for all developers, with no exceptions for individual apps. Infinite Flight owns all Live API data. Keep data only in a short-term cache (latest response for each request, no more than 1 hour). Do not store, accumulate, or share data, including totals and statistics calculated from it. Do not use it to train or improve AI or machine learning models. Stop downloading new data when no user action occurs for 15 minutes. Prohibited use can get the API key and the linked accounts banned.

## Rate Limits

URL: https://infiniteflight.com/guide/developer-reference/api-rules/usage-and-data-rules

- Default: 30 requests per minute per API key.
- 100 requests per minute when the API key is linked to a user account with an active paid Pro subscription.
- If the linked Pro subscription lapses, the key returns to the free-tier default.
- If you cannot keep to the rate limit because your app is popular, contact hello@infiniteflight.com to ask for a higher limit.
- Exceeding the limit returns HTTP `429 Too Many Requests`.

## Changelog

URL: https://infiniteflight.com/guide/developer-reference/live-api/changelog

- **2026-10-20:** Rewrote the usage and data rules to make them clearer. The rules apply to all developers in the same way, with no exceptions. Caches can keep only the latest response for each request, for no more than 1 hour. Statistics and leaderboards calculated from Live API data, and peer-to-peer sharing of cached data, are now named as prohibited. The page also lists the data that you can keep and gives examples. Moved the PublicApi v3 preview docs to their own section (https://infiniteflight.com/guide/developer-reference/live-api-v3/overview), with one page for each endpoint, an OAuth2 page, and a data types page. The llms.txt file now includes PublicApi v3.
- **2026-06-01:** Added `fuelUsedKg` and `landingStats` to Get User Flights and Get User Flight. Both come from the FlightSession/FlightLegs system. `fuelUsedKg` can be null for legacy flights. `landingStats` is empty when landing stats are unavailable.
- **2026-03-18:** Added Get Flight Plans (Bulk), `POST /v2/sessions/{sessionId}/flights/flightplans`: flight plans for up to 10 flights in one request. Fixed an issue where the Flights endpoint could sometimes return an incomplete list of flights during a cache refresh cycle.
- **2026-03-17:** Lowered the default rate limit to 30 requests per minute per API key. Added a higher default limit of 100 requests per minute for API keys linked to users with an active paid Pro subscription. Added usage and polling best practices, including temporary-cache-only storage rules and an explicit prohibition on AI training use of Live API data.
- **2024-04-12:** Added `pilotState` to the Flights endpoint (`Active = 0`, `AwayInFlight = 1`, `AwayParked = 2`, `InBackground = 3`). Fixed missing `airportLatitude` and `airportLongitude` in the ATC endpoint (the current ATC page names these fields `latitude` and `longitude`).
